# Meerkost — multi-line breakdown per configuratie

**Status**: brainstormed, awaiting implementation plan
**Date**: 2026-05-19
**Author**: Kevin (brainstormed with Claude)
**Supersedes**: parts of [2026-05-08 single-meerkost spec](2026-05-08-meerkost-design.md) — schema, persistence, render

## Background

The 2026-05-08 iteration added a single numeric "Meerkost (ex BTW)" input per
configuration, persisted as `meerkostMap: { [type]: number }`. Sales feedback:
this is too coarse. A real project has several distinct extra charges (extra
cabling, additional working hours, certification supplement, etc.), and the
salesperson needs to break those out — both internally for clarity and on the
customer-facing share-link.

This iteration replaces the single-amount field with a list of labelled lines
per configuration. It is also the first step of preparing calculation data
for future automated quote (offerte) generation: each meerkost-line is a
quote line-item in waiting.

## Goals

- Multiple labelled extra-cost lines per config, each with `description` +
  `amount (ex BTW)`.
- Calculation total stays identical to current behaviour: sum of all lines is
  added to the config base price after applying the project BTW rate. ROI/TVT
  are unaffected as a metric, but the install-price grows in line with the
  new lines.
- Display the breakdown in each scenario card so the customer sees what
  drives the install total.
- Forward-compatible structure for a follow-up offerte-generation feature
  (each line maps cleanly to a quote line-item).
- Support both sheet configurations and manual configurations symmetrically.

## Non-goals

- Quantity / unit-price split per line — covered later if a real quote-template
  use case demands it.
- Categorisation (materials / labour / certification) — same as above.
- Per-line BTW override — only relevant when a concrete mixed-rate case
  appears.
- A project-level (outside-calc-run) store of meerkost lines — they live in
  `lastCalcRun.inputs`, same as today.

## Data model

### Line shape

```js
MeerkostLine = {
  id: string,            // _genMeerkostId(), stable for keyed render
  description: string,   // free text, default ""
  amount: number         // ex BTW, >= 0, default 0
}
```

### Container

```js
meerkostLines: { [configType: string]: MeerkostLine[] }
```

The key is the `type` field used elsewhere in calculator code — either a
sheet-config `type` (`zendure-10-h2400`, ...) or a manual-config uuid
generated by `_manualConfigs`. Configs without lines are absent from the map.

Lines whose description is empty AND amount is `0` are stripped at
`_serializeState` time so we don't persist input-row junk. After strip, a
config that ends up with zero meaningful lines is also removed from the map.

### Resolved config (calculator → renderer)

`readAllSelectedConfigObjects()` continues to return one object per active
config. New / renamed fields:

```js
{
  type, omschrijving, batCap, batInv, eff,
  basePrice,                              // sheet sheet-price or manual-price, incl BTW
  price,                                  // basePrice + sum(line.amount * (1+btw/100))
  meerkostLines: [                        // resolved, BTW-applied
    { description, amountExBtw, amountInclBtw }
  ],
  meerkostTotalInclBtw                    // convenience sum
}
```

The old singletons `cfg.meerkost` / `cfg.meerkostInclBtw` are removed from the
output object — the renderer reads `meerkostLines` + `meerkostTotalInclBtw`
exclusively.

Manual configs: same shape. `basePrice` = the manual all-in price the user
typed; meerkost-lines are added on top with project BTW applied.

## Persistence & versioning

### Save format bump: `v: 5` → `v: 6`

`_serializeState()` writes `v: 6`. The only differences vs `v: 5`:
- `meerkostMap` removed from top-level.
- `meerkostLines` added at top-level (`null`/absent when empty).

Everything else (results, inputs, manualConfigs, dailyCompact) is unchanged.

### Read path: `_applyLoadedState(state)`

```
switch (state.v) {
  case 6: lines = state.meerkostLines || {};                              break;
  case 5: lines = _migrateMeerkostMapToLines(state.meerkostMap || {});    break;
  case 1..4: lines = {};                                                  break;  // pre-meerkost saves
}
```

The migrate helper:

```js
function _migrateMeerkostMapToLines(map) {
  const out = {};
  for (const [type, amount] of Object.entries(map || {})) {
    if (typeof amount === 'number' && amount > 0) {
      out[type] = [{ id: _genMeerkostId(), description: 'Meerkost', amount }];
    }
  }
  return out;
}
```

`_applyLoadedState` itself never writes back to Firestore. Read-only paths
(share-link `?s=` and `?data=`) just use the in-memory lazy convert.

### Project-mode write-migration

`loadProjectIntoUI(id)` (the project-mode hydration path behind auth, around
`index.html:2350`) performs a one-time schema upgrade. Sequence:

1. Hydrate state from `proj.lastCalcRun.inputs` as today, via
   `buildSavedFromProject` → `_applyLoadedState`. The v:5 read-fallback in
   `_applyLoadedState` already builds the in-memory `meerkostLines` from the
   legacy map, so the UI is correct regardless of write outcome.
2. After hydration, if `proj.lastCalcRun.inputs.meerkostMap` exists AND
   `proj.lastCalcRun.inputs.meerkostLines` is absent → build the new shape
   via `_migrateMeerkostMapToLines`, then issue one Firestore `.update()`
   with dotted-path keys (same pattern used elsewhere in `firebase-init.js`
   for `lastCalcRun.results`). A small helper in `firebase-init.js`:
   ```js
   async function migrateMeerkostMapToLines(projectId, lines) {
     await projectDoc(projectId).update({
       'lastCalcRun.inputs.meerkostLines': lines,
       'lastCalcRun.inputs.meerkostMap': firebase.firestore.FieldValue.delete(),
       updatedAt: firebase.firestore.FieldValue.serverTimestamp(),
     });
   }
   ```
   This avoids `updateProjectMetadata` because that helper uses
   `set({}, {merge: true})`, which does not honour dotted-path keys —
   they would be written as literal property names containing a dot.
3. Idempotent: a second open finds `meerkostLines` present and skips step 2.
4. Write failure (offline / rules reject) → `console.warn` and continue.
   In-memory state already has the new shape (step 1 handled the read
   fallback); the user can re-trigger the migration on next open.

Read-only paths (share-link `?s=` / `?data=`, non-whitelisted users) never
reach `loadProjectIntoUI`, so there is no risk of an unauthorised write
attempt.

### Share-link / downloaded JSON

- `copyShareLink()` always writes `v: 6` payload (Firestore `shares/<id>` doc
  and the legacy `?data=` base64).
- Already-circulating `v: 5` links keep working via the read-path fallback.
- `downloadSave()` writes `v: 6`; `_applyLoadedState` accepts `v: 1..6`.

## Input UI

Inside each config-picker row, the `<input class="meerkost-input">` is replaced
by a `<details class="meerkost-details">` disclosure:

```
┌─ Configuratie 1 ─────────────────────────────────────────┐
│ [▼ Zendure 10 kWh AC+ Hub 2400 W ........... ]           │
│                                                           │
│ ▾ Meerprijzen (2)                          € 350,00 ex   │
│   ┌──────────────────────────────────────┬──────────┬───┐│
│   │ Omschrijving                         │ Bedrag ex│ ✕ ││
│   ├──────────────────────────────────────┼──────────┼───┤│
│   │ Extra bekabeling 12 m                │     250  │ ✕ ││
│   │ Extra werkuren keuring               │     100  │ ✕ ││
│   └──────────────────────────────────────┴──────────┴───┘│
│   [+ Regel toevoegen]                                     │
└───────────────────────────────────────────────────────────┘
```

Behaviour:

- `<details>` defaults closed; summary text shows `Meerprijzen (N) — €X ex`
  where `N` is the line count and `X` the live sum ex BTW.
- "+ Regel toevoegen" appends an empty `{id, description: "", amount: 0}` row.
  No N+1 trailing-empty pattern (two levels of auto-trailing got cluttered).
- Per row: text input for description, number input for amount (`min="0"
  step="50"`), and ✕ delete button. Delete is non-confirmed — re-adding is
  one click.
- Negative amount forced to 0 on `blur`.
- Empty description is allowed; on display it falls back to "Meerkost #N".
- When the user picks a different config in another picker row,
  `renderConfigPickers` re-renders and preserves the current DOM lines via
  `_readMeerkostLinesFromDom()` merged with any incoming `meerkostLines`
  argument.

CSS additions in the `<style>` block of `index.html`:
- `.meerkost-details` (the wrapper, sits below `.config-picker-row` selectbox)
- `.meerkost-lines-list` (the table container)
- `.meerkost-row` (one line)
- `.meerkost-summary` (the disclosure summary line)
- `.meerkost-add-btn`

In read-only mode (`body.readonly-mode`), the existing greys-out rule for
`.config-picker-row` is extended to cover `.meerkost-details` inputs. The ✕
buttons and "+ Regel toevoegen" button are hidden via CSS in read-only mode
so the disclosure stays informational.

## Results display

### Config-group header

The `(incl. €Y meerkost)` annotation at the top of each configuration block
keeps its current shape. `Y` is now `meerkostTotalInclBtw` instead of the
single-amount value. No annotation when total is zero — same as today.

### Scenario card

Today's single row:

```
Installatieprijs                              € 9.250
```

becomes a `<details class="installprice-details">` disclosure **only if at
least one meerkost line exists** for this config. With zero lines: the row is
unchanged (no chevron, no toggle).

With one or more lines, expanded:

```
▾ Installatieprijs                            € 9.250
   Basis configuratie                          € 8.900
   Extra bekabeling 12 m                       €   263
   Extra werkuren keuring                      €   121
                                              ────────
   Totaal installatie                          € 9.284
```

Rules:
- All amounts incl BTW, using the current project BTW rate.
- `Basis configuratie` row shows `cfg.basePrice` (sheet incl BTW or manual all-in).
- Line description falls back to `Meerkost #N` (1-based) when empty.
- Closing `Totaal installatie` row only present when ≥ 1 line.
- `<details>` defaults closed; Worst Case and Realistisch card disclosure state
  is independent.
- No multi-year-average annotation on these rows (install price doesn't vary
  per year).

The breakdown is identical on the customer-facing read-only share-link.
`<details>` summaries remain clickable in read-only mode (existing CSS only
disables form inputs, not native disclosures).

### Other surfaces

- Energy chart / capacity-analysis / recovery progress bars: no changes.
- `processDataPure`: no changes — it consumes `cfg.price` (the BTW-applied
  total), which already incorporates the lines.

## Code organisation

All changes are inline in `index.html`. `assets/js/calc-engine.js` and
`assets/js/csv.js` are not touched.

| Function | Change |
|---|---|
| `renderConfigPickers(types, meerkostLines)` | Second arg renamed; renders the new disclosure per row instead of the single-input |
| `_readMeerkostFromDom()` → `_readMeerkostLinesFromDom()` | Returns `{ [type]: MeerkostLine[] }` |
| `readAllSelectedConfigObjects()` | Reads lines, sets `cfg.basePrice` + `cfg.price` + `cfg.meerkostLines` + `cfg.meerkostTotalInclBtw`. Also supports manual configs |
| `_serializeState()` | Bumps `v: 6`, writes `meerkostLines`, strips empty rows, removes `meerkostMap` |
| `_applyLoadedState(state)` | Switch on `state.v`; v:5 lazy converts via `_migrateMeerkostMapToLines` |
| `_populateConfigSelects(types, meerkostLines)` | Shim passes 2nd arg through |
| `saveLastCalcRun` callsite | Writes `inputs.meerkostLines` instead of `inputs.meerkostMap` |
| `buildSavedFromProject(proj)` | Reads `inputs.meerkostLines`, with v:5 fallback to `inputs.meerkostMap` |
| `loadProjectIntoUI` | Adds one-time write-migration step (`updateProjectMetadata` patch) after the `_applyLoadedState` call |
| `makeScenCard(d, ..., cfg)` | Receives the full `cfg` (or at least `meerkostLines` + `basePrice`) and renders the install-price disclosure |
| `renderScenarioGrid(d)` | Passes `cfg.meerkostLines` + `cfg.basePrice` to `makeScenCard` |

New small helpers (inline in `index.html`):
- `_genMeerkostId()` — `'mk_' + Math.random().toString(36).slice(2, 10)`
- `_emptyMeerkostLine()` — `{ id: _genMeerkostId(), description: "", amount: 0 }`
- `_sumMeerkostLines(lines, btwPercent)` — total incl BTW
- `_migrateMeerkostMapToLines(map)` — pure converter, used by v:5 read fallback AND project write-migration

Outside `index.html`:
- `assets/js/firebase-init.js` — adds the small `migrateMeerkostMapToLines`
  helper (Firestore `.update()` with dotted-path keys + `FieldValue.delete()`).
- `CLAUDE.md` — update the 2026-05-08 meerkost paragraph: new schema, `v: 6`
  bump, project-load write-migration.
- No `firestore.rules` change needed (`lastCalcRun.inputs` is free-form).

## Testing

E2E coverage (extend existing calculator spec OR new `e2e/tests/meerkost-lines.spec.js`):

1. Add 2 lines in config 1 + 1 line in config 2, click Bereken, assert
   that installatieprijs in WC card == basePrice + Σ (amount × (1 + btw/100))
   for each config.
2. Reload via `?project=<id>` → lines hydrate, not blank.
3. Seed an old project doc with `meerkostMap` via Firebase Admin → open in
   the browser → after load, assert Firestore now contains `meerkostLines`
   and `meerkostMap` is gone.
4. Generate share-link with lines → open in incognito → breakdown visible in
   the scenario card disclosure.

Manual checks:
- 0 lines: no disclosure chevron on `Installatieprijs`, no header annotation.
- 1 line, empty description: renders as "Meerkost #1".
- Read-only mode: ✕ buttons and "+ Regel toevoegen" hidden; disclosure stays
  expandable.
- Switch woning-leeftijd (21% → 6%): re-run Bereken; breakdown amounts update
  with the new BTW rate.
- `downloadSave` + re-upload: lines round-trip intact.

## Migration timeline

- This change is non-breaking for users: old share-links and old project
  saves continue to work via the read-path fallback.
- Project write-migration upgrades schema lazily — no batch migration job
  needed.
- After this ships, new `v: 5` payloads are no longer generated, but
  read-support stays for back-compat.

## Future follow-ups (out of scope here)

- Offerte-export feature: maps `cfg.basePrice` + `meerkostLines` to quote
  line-items, possibly with quantity / unit-price split per line, optional
  category tag, and a header bearing customer / project metadata. The data
  model designed here is intended as the input to that feature.
- Per-line BTW override.
- Per-line category dropdown for grouping in the quote template.
